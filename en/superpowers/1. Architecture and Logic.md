### Layer Responsibilities

| Layer | Responsibility | Key Files |

## 2. Session Bootstrap Flow

```mermaid
sequenceDiagram
    participant U as User
    participant IDE as IDE (Claude Code/Cursor...)
    participant BS as Bootstrap
    participant SE as Skill Engine

    U->>IDE: Start session
    IDE->>BS: Load platform config
    BS->>BS: Read CLAUDE.md / rules
    BS->>SE: Register available skills
    SE->>SE: Index skill frontmatter
    SE->>SE: Build trigger map
    SE-->>IDE: Session ready

    U->>IDE: Send task message
    IDE->>SE: Match task → skills
    SE->>SE: Check 1% trigger rule
    alt Skill matches
        SE->>SE: Load full SKILL.md
        SE-->>IDE: "Using skill: [name]"
        IDE->>IDE: Follow skill process
    else No skill matches
        IDE->>IDE: Respond normally
    end
```

## 3. Skill Resolution Logic

### The 1% Trigger Rule

```mermaid
flowchart TD
    A["User message received"] --> B{"Any skill description<br>matches task context?<br>(even 1% chance)"}
    B -->|"Yes (≥1%)"| C["Read full SKILL.md"]
    C --> D["Announce skill activation"]
    D --> E["Follow skill process"]
    B -->|"Definitely not (0%)"| F["Respond without skill"]
```

**Why 1%?** — Better to invoke a skill unnecessarily than to miss a case where it would have prevented a bug. The cost of reading a SKILL.md is tiny compared to the cost of a missed bug.

### Skill Anatomy

```
skills/
  tdd-workflow/
    SKILL.md                    # Main reference (required)
  systematic-debugging/
    SKILL.md
    root-cause-tracing.md       # Supporting technique
    defense-in-depth.md         # Supporting technique
    find-polluter.sh            # Utility script
```

### SKILL.md Structure

```yaml
---
name: skill-name
description: "Use when [specific triggering conditions]"
---
```

**Body sections:**
1. **Overview** — Core principle in 1-2 sentences
2. **When to Use** — Specific triggers and conditions
3. **The Process** — Step-by-step workflow with checklists
4. **Red Flags** — Signs to STOP and reassess
5. **Common Mistakes** — Anti-patterns and fixes
6. **Integration** — Links to related skills

## 4. Core Skills — Detailed Logic

### 4.1. TDD Workflow (The Iron Law)

```mermaid
flowchart TD
    A["New feature/change request"] --> B["Write failing test"]
    B --> C["Run test → confirm FAILS"]
    C --> D["Write minimal implementation"]
    D --> E["Run test → confirm PASSES"]
    E --> F{"All acceptance<br>criteria covered?"}
    F -->|"No"| B
    F -->|"Yes"| G["Refactor if needed"]
    G --> H["Run all tests → confirm PASS"]
    H --> I["Done ✅"]
```

**Iron Law Rules:**
1. **NEVER** write implementation without a test
2. Tests are written FIRST
3. Implementation is the **minimum** to make tests pass
4. Refactor only after all tests pass
5. No exceptions — not for "simple" changes, not for "config files"

### 4.2. Systematic Debugging

```mermaid
flowchart TD
    A["Test failure / Bug report"] --> B["Read FULL error output"]
    B --> C["Form ≥3 hypotheses"]
    C --> D{"Root cause identified?"}
    D -->|"Yes"| E["Apply targeted fix"]
    D -->|"No"| F["Run root-cause-tracing"]
    F --> G["Binary search through code"]
    G --> D
    E --> H["Defense-in-depth check"]
    H --> I{"Same class of bugs<br>possible elsewhere?"}
    I -->|"Yes"| J["Find and fix all instances"]
    I -->|"No"| K["Done ✅"]
    J --> K
```

**Key sub-skills:**
- **Root Cause Tracing** — Binary search through code to find the actual cause
- **Defense-in-Depth** — After fixing a bug, check if the same class of bugs exists elsewhere
- **Find Polluter** — When tests pass alone but fail together, find which test contaminates state

### 4.3. Brainstorming

```mermaid
flowchart TD
    A["Complex task"] --> B["Generate ≥3 approaches"]
    B --> C["Evaluate each approach<br>Pros/Cons/Risks"]
    C --> D["Select best approach"]
    D --> E["Document decision rationale"]
    E --> F["Proceed to implementation"]
```

**Mandatory for:**
- Subagent tasks (always brainstorm before implementing)
- Architecture decisions
- Complex debugging

### 4.4. Rethinking

**Trigger:** When the current approach isn't working.

```mermaid
flowchart TD
    A["Current approach failing"] --> B["STOP"]
    B --> C["Question fundamental assumptions"]
    C --> D["Generate ≥3 alternative approaches"]
    D --> E["Evaluate alternatives"]
    E --> F["Select new approach"]
    F --> G["Start fresh with new approach"]
```

## 5. Subagent Architecture

### 5.1. Subagent-Driven Development Flow

```mermaid
sequenceDiagram
    participant C as Controller
    participant B as Brainstorm Subagent
    participant I as Implement Subagent
    participant R1 as Spec Reviewer
    participant R2 as Quality Reviewer

    C->>B: Task description + context
    B->>B: Generate approaches
    B-->>C: Selected approach + rationale

    C->>I: Approach + spec + context
    Note over I: Fresh context window
    I->>I: Write tests first (TDD)
    I->>I: Implement to pass tests
    I-->>C: Completed code

    C->>R1: Code + original spec
    R1->>R1: Does code match spec?
    R1-->>C: Spec review result

    C->>R2: Code + quality criteria
    R2->>R2: Code quality, edge cases, performance
    R2-->>C: Quality review result

    alt Both reviews pass
        C->>C: Accept changes ✅
    else Issues found
        C->>I: Fix identified issues
        I-->>C: Updated code
        Note over C: Re-review cycle
    end
```

### 5.2. Status Protocol

Each subagent reports one of:

| Status | Meaning | Controller Action |
|---|---|---|
| `DONE` | Task completed successfully | Proceed to review |
| `DONE_WITH_CONCERNS` | Completed but has caveats | Note concerns for review |
| `NEEDS_CONTEXT` | Missing information | Provide context, re-dispatch |
| `BLOCKED` | Cannot proceed | Assess: re-dispatch with more context or escalate |

### 5.3. When to Use Subagents

| Task Complexity | Approach |
|---|---|
| Simple (< 50 lines change) | Direct implementation |
| Medium (50-200 lines) | Consider subagent |
| Complex (> 200 lines) | **Always** use subagent |
| Multiple file changes | **Always** use subagent |
| Architecture decisions | Brainstorm subagent first |

## 6. Model Selection Strategy

Superpowers suggests appropriate models based on task type:

| Task Type | Recommended Model | Reason |
|---|---|---|
| **Architecture decisions** | Most capable (Opus) | Needs deep reasoning |
| **Implementation** | Balanced (Sonnet) | Code generation sweet spot |
| **Test writing** | Balanced (Sonnet) | Needs understanding of implementation |
| **Code review** | Balanced (Sonnet) | Pattern recognition |
| **Simple refactoring** | Fast (Haiku) | Mechanical changes |
| **Documentation** | Fast (Haiku) | Straightforward generation |

## 7. Error Handling

| Error | Skill Response |
|---|---|
| Tests fail after implementation | → systematic-debugging skill |
| Can't find root cause | → root-cause-tracing (binary search) |
| Tests pass alone but fail together | → find-polluter skill |
| Fix creates new bugs | → defense-in-depth check |
| Current approach isn't working | → rethinking skill |
| Task too complex for one context | → subagent decomposition |
